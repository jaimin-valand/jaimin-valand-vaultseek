# Private Search Engine v2.3 - Remote Shards & Fault Tolerance

v2.3 turns the local sharding model into a dependency-light remote-shard architecture.

## Components

- `RemoteShardNode`: HTTP client for a shard node.
- `ShardNodeServer`: standard-library HTTP shard service (`/health`, `/documents`, `/search`, `/stats`).
- `RemoteShardCoordinator`: parallel fan-out/fan-in coordinator.
- Retry with bounded exponential backoff.
- Circuit breaker to stop repeatedly calling an unhealthy node.
- Partial-result semantics: healthy shards can still return results when another shard fails.
- Per-node health and latency telemetry.
- Deterministic global score/doc-id merge.

## Running a shard node

```bash
python -m private_search_engine.cli remote-node --port 8001 --node-id shard-0
```

Start additional nodes on different ports. The shard server is intentionally implemented with Python's standard library so the distributed layer can be tested without a service mesh or external infrastructure.

## Remote search

```bash
python -m private_search_engine.cli remote-search "python systems" \
  --nodes http://127.0.0.1:8001 http://127.0.0.1:8002
```

The coordinator reports whether the result set is partial and which nodes are unhealthy.

## Fault model

The coordinator treats connection errors, HTTP errors, timeouts and malformed responses as shard failures. Failed calls are retried according to the node policy. Once the configured failure threshold is reached, the circuit opens and subsequent requests skip the node until the reset timeout expires.

This is a local deterministic fault-tolerance layer, not a claim of consensus, replication, or production-grade distributed storage.
